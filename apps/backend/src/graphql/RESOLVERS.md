# Resolver audit — cross-referenced against frontend usage

## What was checked

Every GraphQL query/field exposed by `resolvers/*.ts` was cross-referenced
against actual consumers in this monorepo:

- `apps/frontend/src` — no `apollo-client`/`@apollo/client`, no
  `graphql-request`, no `gql\`...\`` template literals, and no fetch calls to
  a `/graphql` endpoint anywhere in the frontend source.
- `packages/mobile-app` — same result, no GraphQL client dependency or usage.
- No other package in the workspace imports a GraphQL client.

The frontend talks to the backend exclusively over the REST endpoints under
`apps/backend/src/**/*.controller.ts` via `apps/frontend/src/lib/apiClient.ts`
and friends.

## Finding

Unlike the "some fields are stale after schema evolution" framing in the
original issue, the actual state is broader: **none** of the three resolvers
— `CourseResolver` (`course`, `courses`, `instructor`), `UserResolver`
(`user`, `users`, `progress`), `ProgressResolver` (`progressByUser`) — are
queried by any in-repo consumer. `apps/backend/package.json` is the only
place in the workspace that depends on a GraphQL client/server library, and
that dependency is the server itself (`@nestjs/graphql`), not a consumer.

## What this change does

- Removes a piece of dead code inside `CourseResolver.courses()`: a
  `this.coursesService.findAll ? ... : { data: [], meta: {} }` fallback for a
  method that unconditionally exists on `CoursesService` — the branch could
  never execute the fallback and was left over from an earlier, less certain
  version of the resolver.
- Documents the audit result here rather than unilaterally deleting the
  GraphQL module: removing a whole subsystem is a bigger call than this pass
  should make on its own, since a consumer outside this repository (a partner
  integration, an internal tool, a Postman/Insomnia collection someone relies
  on) can't be ruled out from repo evidence alone.

## Recommended follow-up (needs a maintainer decision, not made here)

Given zero in-repo consumers, a maintainer should decide between:

1. **Deprecate and remove** `apps/backend/src/graphql/*` and the
   `AppGraphQLModule` import in `app.module.ts`, plus the `@nestjs/graphql` /
   `apollo-server-*` dependencies, if nothing external depends on it.
2. **Keep it and wire up a real consumer** if the GraphQL API is intentional
   (e.g. planned for the mobile app or an external partner API), in which
   case it should gain integration tests and be added to API documentation
   like the REST endpoints already have.

## Schema regeneration

`graphql.module.ts` uses `autoSchemaFile` pointed at
`packages/types/src/schema.gql` — the SDL file is generated by NestJS at
application bootstrap, not authored by hand, and is not currently committed
to the repo (no `schema.gql` exists in `packages/types/src` as of this
change). It is regenerated automatically the next time the backend boots
against these resolvers; there is no stale committed schema file to reconcile
in this change.
